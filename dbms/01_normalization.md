# StudyMate AI · Normalization (UNF → 1NF → 2NF → 3NF → BCNF)

## 0. The app in one paragraph

**StudyMate AI** is a study app built around one idea from chess: **every question is an opponent.**
Each student has an **Elo rating per subject** (like a chess rating), and so does every question. Answering a question is a "game": beat a hard question and your rating goes up a lot, miss an easy one and it drops. The question's rating moves the other way, so difficulty stays honest without anyone setting it by hand.
On top of that:

- **Quiz duels.** Two students play the same quiz live, as **White and Black**, on a **chess clock** (e.g. *Blitz 3+2*: 3 minutes plus 2 seconds per answered question). A duel ends on score, **resignation** or **timeout**, and both ratings change.
- **Titles.** Ratings unlock chess-style titles per subject: *Physics FM*, *Maths GM*, and so on.
- **Focus sessions with chess-puzzle breaks.** A Pomodoro study timer (25 or 50 min); the break is a short chess puzzle.
- **AI Mistake Notebook.** Every question you get wrong is saved with an **AI-written explanation** and comes back for revision on a spaced-repetition schedule (Leitner boxes 1–5).
- **AI quiz generation** and **coaches.** Quizzes and questions can be generated by AI. High-rated students can become a **coach** for one subject.

The app's data comes from two "documents" a user sees. We normalize both:

| Source | What it is |
|---|---|
| **A. Duel scoresheet** | Like a chess scoresheet: players, clock, and every "move" (question) with both players' answers |
| **B. Student profile** | A student's ratings, focus sessions with puzzles, mistake notebook and coaches |

## 1. Unnormalized form (UNF)

### A. Duel scoresheet (one per duel)

```

WHITE  aarav_k (aarav@mail.com) · Riverbank Institute of Technology, Dehradun · 1642 (CM)
BLACK  riya_s  (riya@mail.com)  · Lakeside Engineering College, Jaipur        · 1588 (Club)

Move | Question (topic, rating)                                    | Options                              | Key | White     | Black
  1  | 1001 Ball dropped from 20 m, time to fall? (Kinematics, 1450)| A) 1 s  B) 2 s  C) 4 s  D) √2 s      |  B  | B · 7.2 s | B · 9.8 s
  2  | 1002 Slope of a v–t graph gives? (Kinematics, 1380)         | A) displacement B) speed C) accel. D) jerk | C | C · 4.1 s | A · 6.0 s
  3  | 1003 Unit of momentum? (Laws of Motion, 1200)               | A) kg·m/s B) N/s C) J·s D) kg/m·s    |  A  | A · 3.3 s | A · 2.9 s

Result 1-0 (by score 3–2) · White +14 → 1656 · Black −14 → 1574
```

As a relation, with repeating groups in `{ }`:

```
DUEL_SHEET( duel_id, played_on, subject, quiz_id, quiz_title, time_control,
            { color, username, email, college, college_city, rating_before, title, rating_change },
            { move_no, question_id, question_text, topic, question_rating,
              { option_letter, option_text }, correct_option,
              { color, chosen_option, time_taken } },
            result )
```

### B. Student profile (one per student)

```
STUDENT_PROFILE( user_id, username, email, college, college_city,
                 { subject, rating, title },
                 { session_id, subject, started_at, ended_at, planned_minutes,
                   puzzle_id, puzzle_fen, puzzle_solution, puzzle_rating, puzzle_theme, puzzle_solved },
                 { question_id, question_text, ai_explanation, leitner_box, next_review_on },
                 { subject, coach_username } )
```

**Why UNF is a problem:**
- **Repeating groups:** players, moves, the options inside a move, and answers inside a move.
- **Non-atomic values:** `"Blitz 3+2"` hides two numbers; `"1-0 (by score 3–2)"` mixes result and reason; `"7.2 s"` mixes number and unit.
- **No usable key:** you can't point at "Black's answer to move 2" with a key.

## 2. First normal form (1NF)

**Rule:** every cell holds one atomic value, there are no repeating groups, and every row has a primary key.

**What we did:**
- Split `time_control` into `base_seconds = 180` and `increment_seconds = 2`. The name "Blitz" isn't stored, because it can be computed from `base_seconds` (bullet < 3 min, blitz 3–10, rapid > 10).
- Split the result into `result = '1-0'` and `termination = 'SCORE'` (other values: `RESIGN`, `TIMEOUT`).
- Store times as numbers (`time_taken_ms = 7200`).
- Flattened the duel into **one row per player per move**.
- Options repeat per question, not per player, so we moved them to their own relation carrying the question's key.

### A. Duel → 1NF

**DUEL_1NF** (PK = `duel_id, color, move_no`)

### Functional dependencies found in 1NF

| # | FD | Kind (w.r.t. the PK) |
|---|---|---|
| F1 | `duel_id → played_on, base_seconds, increment_seconds, result, termination, quiz_id` | **partial** (only part of `duel_id, color, move_no`) |
| F2 | `quiz_id → quiz_title, subject_name` | **transitive** |
| F3 | `duel_id, color → user_id, rating_before, rating_change` | **partial** |
| F4 | `user_id → username, email, college_name` | **transitive** |
| F5 | `college_name → college_city` | **transitive** |
| F6 | `rating → title` (a title is a rating band: CM ≥ 1600, FM ≥ 1800 …) | **transitive** |
| F7 | `quiz_id, move_no → question_id` (both players get the same question at the same move) | **partial** (via `duel_id → quiz_id`) |
| F8 | `question_id → question_text, topic_name, question_rating` | **transitive** |
| F9 | `topic_name → subject_name` | **transitive** |
| F10 | `duel_id, color, move_no → chosen_option, time_taken_ms` | **full**: the only "good" FD |
| F11 | `puzzle_id → puzzle_fen, puzzle_solution, puzzle_rating, puzzle_theme` | **transitive** (in SESSIONS) |
| F12 | `question_id → question_text` | **partial** (in MISTAKES, key `user_id, question_id`) |
| F13 | `student_id, subject_name → coach_id` and `coach_id → subject_name` | see BCNF |

**Anomalies still present in 1NF:**
- **Update:** if aarav_k changes his email, 3 rows per duel × every duel he played must change. Missing one gives two emails for one user.
- **Insert:** a new question can't be stored until it has been played in a duel (no `duel_id` → no key).
- **Delete:** deleting the only duel that used question 1003 also deletes the question.

## 3. Second normal form (2NF)

**Rule:** 1NF **and** no non-key attribute depends on only *part* of a composite key.

DUEL_1NF has the composite key `(duel_id, color, move_no)`, so we split it by which part of the key each attribute depends on (F1, F3, F7):

```
DUELS_2NF        ( duel_id, played_on, base_seconds, increment_seconds, result, termination,
                   quiz_id, quiz_title, subject_name )                                   PK duel_id
DUEL_PLAYERS_2NF ( duel_id, color, user_id, username, email, college_name, college_city,
                   rating_before, title, rating_change )                                 PK (duel_id, color)
DUEL_MOVES_2NF   ( duel_id, move_no, question_id, question_text, topic_name,
                   subject_name, question_rating )                                       PK (duel_id, move_no)
DUEL_ANSWERS_2NF ( duel_id, color, move_no, chosen_option, time_taken_ms )               PK (duel_id, color, move_no)
QUESTION_OPTIONS ( question_id, option_no, option_text, is_correct )                     PK (question_id, option_no)  ✓ already 2NF
```

Profile side (only relations with a composite key can break 2NF):

| Relation | Partial dependency? | Fix |
|---|---|---|
| RATINGS_1NF `(user_id, subject_name)` | `rating`, `title` need both parts → none | — |
| MISTAKES_1NF `(user_id, question_id)` | **F12** `question_id → question_text` | Remove `question_text`; it lives with the question |
| COACHING_1NF `(student_id, subject_name)` | `coach_id` needs both parts → none | — |
| PROFILE_1NF, SESSIONS_1NF | single-column key → **automatically 2NF** | — |

```
MISTAKES_2NF ( user_id, question_id, ai_explanation, leitner_box, next_review_on )      PK (user_id, question_id)
```

`ai_explanation` stays here, not in QUESTIONS: the AI explains **this student's** mistake (it looks at what they chose), so it depends on the whole key.

**Fixed:** a question can now exist without any duel, and a user's email appears once per duel instead of once per move.
**Still wrong:** `username`, `email` and `college_city` still repeat in every duel the user plays (transitive dependencies).

## 4. Third normal form (3NF)

**Rule:** 2NF **and** no non-key attribute depends on another non-key attribute (no transitive dependency `key → A → B`).

| Relation | Transitive dependency | Fix: new relation |
|---|---|---|
| DUELS_2NF | `duel_id → quiz_id → quiz_title, subject` (F2) | **QUIZZES**(quiz_id, title, subject_id) |
| DUEL_PLAYERS_2NF | `… → user_id → username, email, college` (F4) | **USERS**(user_id, username, email, college_id) |
| DUEL_PLAYERS_2NF, PROFILE_1NF | `user_id → college → city` (F5) | **COLLEGES**(college_id, college_name, city) |
| DUEL_PLAYERS_2NF, RATINGS_1NF | `rating → title` (F6) | **TITLES**(title_code, title_name, min_rating); title is looked up, never stored |
| DUEL_MOVES_2NF | `(duel, move) → question_id → text, topic, rating` (F8) | **QUESTIONS**(question_id, topic_id, question_text, question_rating) |
| DUEL_MOVES_2NF | `question → topic → subject` (F9) | **TOPICS**(topic_id, subject_id, topic_name), **SUBJECTS**(subject_id, subject_name) |
| DUEL_MOVES_2NF | `(duel, move) → question` is really `(quiz, position) → question` (F7) | **QUIZ_QUESTIONS**(quiz_id, position, question_id) |
| SESSIONS_1NF | `session_id → puzzle_id → fen, solution, rating, theme` (F11) | **CHESS_PUZZLES**(puzzle_id, fen, solution_moves, puzzle_rating, theme) |

**One more step: practice and duels share "attempts".** A student also plays quizzes alone (practice). Instead of separate answer tables for practice and duels, every play of a quiz becomes an **attempt** (`attempt_id`). A duel player is simply an attempt that belongs to a duel:

- `(duel_id, color)` → is now identified by an `attempt_id`.
- DUEL_ANSWERS → **ATTEMPT_ANSWERS**(attempt_id, question_id, chosen_option_no, time_taken_ms).
- The duel's quiz and each player's user come **from their attempts**, so DUELS no longer stores `quiz_id`. Storing it would create `duel_id → quiz_id` next to `attempt_id → quiz_id`, the same fact twice.

### 3NF relations

```
COLLEGES        ( college_id, college_name, city )
USERS           ( user_id, username, email, full_name, password_hash, college_id, created_at )
SUBJECTS        ( subject_id, subject_name )
TOPICS          ( topic_id, subject_id, topic_name )
TITLES          ( title_code, title_name, min_rating )
USER_RATINGS    ( user_id, subject_id, rating, updated_at )
QUESTIONS       ( question_id, topic_id, question_text, question_rating, source, created_by )
QUESTION_OPTIONS( question_id, option_no, option_text, is_correct )
QUIZZES         ( quiz_id, title, subject_id, is_ai_generated, created_by, created_at )
QUIZ_QUESTIONS  ( quiz_id, position, question_id )
QUIZ_ATTEMPTS   ( attempt_id, quiz_id, user_id, started_at, finished_at )
ATTEMPT_ANSWERS ( attempt_id, question_id, chosen_option_no, time_taken_ms )
DUELS           ( duel_id, base_seconds, increment_seconds, result, termination, started_at, ended_at )
DUEL_PLAYERS    ( duel_id, color, attempt_id, rating_before, rating_change )
CHESS_PUZZLES   ( puzzle_id, fen, solution_moves, puzzle_rating, theme )
STUDY_SESSIONS  ( session_id, user_id, subject_id, started_at, ended_at, planned_minutes, puzzle_id, puzzle_solved )
MISTAKE_NOTEBOOK( user_id, question_id, ai_explanation, leitner_box, next_review_on, added_at )
COACHING_3NF    ( student_id, subject_id, coach_id )          ← 3NF but not BCNF, see below
```

**Fixed:** a user's name, email and college are stored once. A question's text is stored once, however many quizzes, duels or notebooks use it. A puzzle's FEN is stored once, however many sessions use it.

## 5. Boyce–Codd normal form (BCNF)

**Rule:** for **every** FD `X → Y`, X must be a superkey. 3NF still allows `X → Y` when Y is part of *some* candidate key; BCNF does not.

### The coaching problem

Rules of the coach feature:
1. A student has **one coach per subject** → `student_id, subject_id → coach_id`
2. A coach coaches **exactly one subject** → `coach_id → subject_id`

| student_id | subject_id | coach_id |
|---|---|---|
| aarav_k | Maths | meera_t |
| riya_s | Maths | meera_t |
| riya_s | Physics | kabir_d |
| dev_p | Maths | arjun_r |

- Candidate keys: `{student_id, subject_id}` and `{student_id, coach_id}`.
- Every attribute is part of some key (all are *prime*), so the table **is in 3NF**.
- But `coach_id → subject_id` and `coach_id` is **not a superkey**, so it **breaks BCNF**.
- **Anomalies:** "meera_t teaches Maths" is repeated for each of her students. If she switches subject, many rows must change. A new coach's subject can't be recorded until they have a student. If dev_p leaves, we lose the fact that arjun_r coaches Maths.

**Decomposition** (split on the bad FD `coach_id → subject_id`):

```
COACHES  ( coach_id, subject_id )        PK coach_id            -- a coach is a user (FK → USERS)
COACHING ( student_id, coach_id )        PK (student_id, coach_id)
```

- **Lossless:** the shared column `coach_id` is the key of COACHES, so joining them back gives exactly the original rows.
- **Trade-off:** the FD `student_id, subject_id → coach_id` is **no longer inside one table**, so the database can't stop a student from taking two Maths coaches with a simple key. We enforce it in the app (or a trigger). We accept this because it removes all the anomalies above.

| COLLEGES | {college_id}, {college_name, city} | key → all | ✅ |

## 6. Final schema (BCNF)

| # | Table | Primary key | Foreign keys | Purpose |
|---|---|---|---|---|
| 1 | colleges | college_id | — | College leaderboards |
| 2 | users | user_id | college_id → colleges | Students (and coaches) |
| 3 | subjects | subject_id | — | Physics, Maths, … |
| 4 | topics | topic_id | subject_id → subjects | Kinematics, Laws of Motion, … |
| 5 | titles | title_code | — | Club < 1600, CM ≥ 1600, FM ≥ 1800, IM ≥ 2000, GM ≥ 2200 |
| 6 | user_ratings | (user_id, subject_id) | user_id → users, subject_id → subjects | Current Elo per subject |
| 7 | questions | question_id | topic_id → topics, created_by → users | Text + Elo difficulty; `source` = AI / TEACHER / STUDENT |
| 8 | question_options | (question_id, option_no) | question_id → questions | Exactly one option per question is correct |
| 9 | quizzes | quiz_id | subject_id → subjects, created_by → users | AI-generated or hand-made |
| 10 | quiz_questions | (quiz_id, position) | quiz_id → quizzes, question_id → questions | Order of questions ("moves") |
| 11 | quiz_attempts | attempt_id | quiz_id → quizzes, user_id → users | One play of a quiz (practice or duel) |
| 12 | attempt_answers | (attempt_id, question_id) | attempt_id → quiz_attempts, (question_id, chosen_option_no) → question_options | What was chosen, how fast |
| 13 | duels | duel_id | — | Clock (base + increment), result 1-0 / 0-1 / ½-½, termination |
| 14 | duel_players | (duel_id, color) | duel_id → duels, attempt_id → quiz_attempts | White / Black, rating before and change |
| 15 | chess_puzzles | puzzle_id | — | FEN, solution (UCI), rating, theme |
| 16 | study_sessions | session_id | user_id → users, subject_id → subjects, puzzle_id → chess_puzzles | Pomodoro session + puzzle break |
| 17 | mistake_notebook | (user_id, question_id) | user_id → users, question_id → questions | AI explanation + spaced-repetition box |
| 18 | coaches | coach_id | coach_id → users, subject_id → subjects | One subject per coach |
| 19 | coaching | (student_id, coach_id) | student_id → users, coach_id → coaches | Who is coached by whom |

### Values we deliberately do **not** store (computed when needed)

| Value | Computed from | Why not stored |
|---|---|---|
| Score of an attempt | count of `attempt_answers` whose chosen option has `is_correct` | Would repeat information already in the answers; could go out of sync |
| Was an answer correct? | `question_options.is_correct` of the chosen option | Same reason |
| Title (CM, FM, …) | `user_ratings.rating` against `titles.min_rating` | Changes every time the rating changes (F6) |
| Time-control name (Blitz, Rapid) | `duels.base_seconds` | Derived from a stored number |
| Actual study minutes | `ended_at − started_at` | Derived |
| A duel's quiz and players | their `quiz_attempts` | Already stored once in the attempt |

### Values that look derived but are kept (history)

- **`duel_players.rating_before` and `rating_change`:** the rating *at the time of that duel*. The current rating in `user_ratings` keeps changing, and the old value can't be recomputed without replaying every game ever played. It depends on the key `(duel_id, color)`, so it doesn't break any normal form.
- **`duels.result` and `termination`:** a duel can end by **resignation or timeout**, so the result can't always be computed from the two scores.
